# Data Model: MVP Foundation

## Overview

Supabase Auth owns credentials and the canonical authenticated user identifier. Application
tables in the public schema store only the minimum profile and authorization data needed for
the foundation. Future animal, questionnaire, application, appointment, and AI tables are
outside this feature and must receive their own migrations and RLS policies.

## Entities

### Authenticated User

Managed by Supabase Auth as `auth.users`.

- **Identity**: UUID user id.
- **Credentials**: Email/password managed by Supabase Auth; passwords are never stored in
  application tables.
- **Lifecycle**: Created, signed in, signed out, recovery requested, or disabled by Auth.
- **Relationship**: One-to-one with `profiles` and one-to-one with `role_assignments`.

### Profile

Application-owned basic information for an authenticated user.

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Primary key and foreign key to `auth.users.id`; cascade on user deletion |
| `display_name` | Text, nullable | User-editable, length-limited, trimmed |
| `created_at` | Timestamp | Set by the database |
| `updated_at` | Timestamp | Updated by the database on permitted profile changes |

### Role Assignment

The authorization source of truth for the foundation.

| Field | Type | Rules |
|---|---|---|
| `user_id` | UUID | Primary key and foreign key to `auth.users.id`; cascade on user deletion |
| `role` | Enum | `applicant` or `staff`; not writable by normal browser clients |
| `created_at` | Timestamp | Set by the database |
| `updated_at` | Timestamp | Set by trusted provisioning operations |

New self-registrations receive `applicant` through a trusted database-side creation path.
Staff assignments require a trusted provisioning operation. There is no self-service role
promotion and no client-side fallback to staff.

### Application Shell

UI state derived from the authenticated session and role assignment. It is not persisted as a
database entity.

- **Public shell**: Landing, sign-in, registration, recovery, and reset entry points.
- **Applicant shell**: Authenticated home, account, and labeled future-feature placeholders.
- **Staff shell**: Staff home, account, and labeled future-feature placeholders.
- **Invalid state**: Missing or unrecognized role; deny privileged access and show recovery.

## Relationships

```text
auth.users 1 ─── 1 profiles
auth.users 1 ─── 1 role_assignments
```

## Validation Rules

- A profile and role assignment MUST reference an existing Auth user.
- A user MUST have exactly one recognized foundation role before protected shell access is
  granted.
- `role_assignments.role` MUST accept only `applicant` or `staff`.
- Browser clients MAY read only their own profile and role assignment.
- Browser clients MAY update only permitted profile fields for their own profile.
- Browser clients MUST NOT insert, update, or delete role assignments.
- Missing, duplicate, revoked, or invalid role data MUST fail closed.
- Timestamps MUST be generated by the database rather than trusted client input.

## Row Level Security Policy Matrix

| Resource | Anonymous | Applicant | Staff | Trusted provisioning |
|---|---|---|---|---|
| `profiles` | No access | Select/update own permitted fields | Select/update own permitted fields | Full migration/provisioning access |
| `role_assignments` | No access | Select own row | Select own row | Insert/update/delete |

RLS MUST be enabled before any application table is exposed. Grants and policies MUST be tested
together; policies alone are not sufficient authorization.

## Deferred Domain Entities

The following entities remain intentionally deferred to later features: animals, animal photos,
questionnaire questions and answers, compatibility results, adoption applications, appointments,
email notifications, and AI conversations.
